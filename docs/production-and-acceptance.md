# 制作管理、阶段门与人工验收

当前：**M0 已合并；M1 仅 C01-L01 灰盒及技术验证获批，交付后等待真人试玩与用户反馈**。长期规模不构成工作队列。运行、证据和范围卡见 [L01 灰盒记录](m1-c01-l01.md)。

## 里程碑与阶段的关系

| 层级/里程碑 | 合法工作 | 退出与停止条件 |
| --- | --- | --- |
| M0 已合并 | 整体架构、研究/API 核查、章节路线、第一章详设与设计推演、持久化规范 | 历史交付，不代表全部单元均获制作批准 |
| M1 当前，仅 L01 获批 | C01-L01 灰盒及不可分割的最低公共能力、浏览器技术验证 | 提交/推送后停止等待用户实际体验，不能顺带铺满第一章 |
| 后续逐关阶段 | 同一关按下表逐步推进；新关另给范围 | 未过所需用户验收不开始下阶段/下一关 |
| 章节整合，尚未授权 | 仅当章内已完成的关卡允许连接后，检查转换、叙事状态与节奏 | 章节真实通关和用户体验验收；不能用整合名义补造未获批关卡 |
| 全局收束/发布，尚未授权 | 全流程、结局、设备与部署，单独计划 | 完整人工审查及明确发布指令，Codex 不自行发布 |

M1 是后续小范围开发的起点，不意味着“一口气完成第一章”。用户可以只批准设计修订，也可以只批准某关灰盒。每次任务仍要注明具体阶段。

## 每关七阶段

| 阶段 | 本阶段交付 | 必须验证/人工判断 | 停止与回退 |
| --- | --- | --- | --- |
| 1 设计审查 | 稳定 ID、空间图/剖面、尺度、首视线、机关关系、完整解法、替代行为、状态/检查点、风险 | 用户审查独特性、可理解性、原创性和范围；设计推演发现的矛盾先修正 | 未通过则只改设计；禁止建邻关占位 |
| 2 灰盒实现 | 只建当前单元和最低测试入口，真实输入/碰撞/机关/重试；调试与正式内容分开标明 | 拟定路线技术可达；真实交互而非控制台解锁；基本性能与异常无阻塞 | 技术不成立回到设计；不能称正式场景 |
| 3 实际可玩性验证 | 真实输入录屏/操作记录、测试者与设备、初见行为、完成/卡住证据 | 没读解法的玩家能识别目标并推理；不能只让作者照最优路线走 | 无测试者时明确“待测”，不以自动化或推演代替 |
| 4 谜题迭代 | 根据观察修改信息、路线、容差、重试；给出前后差异 | 新测试验证原误读是否消失、是否破坏顿悟；用户确认可进入美术 | 允许删关/换结构；不拿已写代码作否决理由 |
| 5 正式美术 | 原创/授权模型、材质、灯光、碰撞、比例与性能记录 | 视线/可交互性和灰盒解法保持；用户检查空间质量，不用基础几何冒充成品 | 可读性变差回退布局/视觉；不批量美化未经验证的房间 |
| 6 叙事演出 | 音效、字幕、短广播、环境状态和角色事件；有声/静音都能理解 | 事件是操作后果，没听完不锁路，存档不重复/漏演，演出不掩盖重要反馈 | 生硬或冗长就删改，不用日志替代体验 |
| 7 综合验收 | 连续真实通关、替代行为、软锁/重试、暂停/失焦、持久继续、目标设备证据 | 用户确认谜题、空间、叙事、美术与舒适度；所有阻塞风险关闭或明确缩减 | 没有用户验收不得标 Done，不制作下一关替代修复 |

实施阶段的公共系统改动须能追溯到当前单元需要。不能以“顺便准备未来”为由实现所有机制、关卡加载表或后期设备。

## 第一章制作顺序（仅 L01 当前阶段已批准）

入口选择以 C01-L01 为最小空间验证对象。S01 的最低操作教学只有得到明确同组授权才纳入，不默认捆绑。

| 顺序 | 单元/工作 | 先解决的问题 | 前置验收与边界 |
| --- | --- | --- | --- |
| 0 | M0 文档审查/修订 | 世界观、第一章路线、教学量、技术约束是否成立 | M0 已合并；后续仍可依据游玩修订 |
| 1 | C01-L01 侧向通行 | 固定折口的目标可读性、层高、穿越与实体返回路 | 当前只批准灰盒与技术验证；真人试玩、美术、演出和综合验收未通过 |
| 2 | C01-S01 复压值守室 | 普通拿放和局部反馈是否足够教学而不拖延 | L01 体验基线可用；只做此短序列，除非此前已明确批准其与 L01 同组 |
| 3 | C01-L02 隔栏借物 | 窄口、真实路径抓取、坞座反馈、门安全 | L01/S01 通过需要的人工验收；先技术容差再美术，不提前建 S02 |
| 4 | C01-S02 卷闸背面 | 玩家是否把封闭认作自己的操作后果；补气是否有价值 | L02 实际反馈已定；只连接已验收端点 |
| 5 | C01-L03 回望接驳 | 高低视线、端点保留、绕回起点是否有顿悟；捷径是否合法 | L02/S02 学习与剧情成立；可退回详设改梁/落台 |
| 6 | C01-S03 候潮眺台 | 亲手确认下一目标，而非播长篇章节总结 | L03 通过；只做第一章出口，不建 C02 占位 |
| 7 | 第一章整合（另立任务） | 实体连接、折口安全交接、检查点/回访、完整节奏 | 六单元满足整合条件并获用户授权后，真实通关再验收 |

此顺序体现风险优先，不宣称先做完灰盒再把整章一并美术化。允许用户要求先完成 L01 某一阶段再停止，或在单关已综合验收后进入下一单元。

## 真实试玩/验收记录模板

```text
单元 / 资产版本 / 引擎 SHA / 测试日期：
测试者（是否初见、是否事先看过解法）：
设备 / 浏览器 / 输入 / 性能与舒适度设置：
起始存档与路线：
第一眼看到的目标 / 首次尝试 / 误读：
顿悟如何发生（观察或玩家原话，而非作者猜测）：
实际通过/失败/中断、用时、提示层级、重试次数：
替代行为、越界、丢物、存档/后台恢复结果：
录像/截图/日志证据：
需修订的空间、提示、碰撞或叙事：
用户验收意见、允许进入的下一阶段、日期：
```

不能只报“能跑、测试全绿、通关成功”。作者照着解法通关可以验证操作链，却不能证明初见可理解。程序化夹具可检查边界，不计入盲测人数。

## M0 的文档检查与审查问题

M0 检查应覆盖内部链接、ID/计数、机制先修、空间坐标与落脚区、折口物理与逻辑路的区别、供电→卷闸→回访的因果、存档/恢复/广播幂等，以及所有“已验证”陈述的证据范围。源码测试与设计推演分别记录，不把它们升级为游戏验收。

需要用户判断的内容：

1. 澄湾站的公共设施背景、林岑/衡务/许澈的冲突是否具有本作辨识度。
2. 章内多个单元是否形成连贯建筑与节奏；是否存在可以删去而不损失新认识的候选。
3. 第一章固定折口、跨门取物、自主接驳的递进是否过密，供电后果是否可见而不过早揭底。
4. 第一章精细图是否足以进入单关灰盒验证；哪些几何/叙事假设必须先改。
5. 三个结局是否都有明确代价、完整体验与知情选择；共管是否显得无代价优解。
6. 承载投射与货流是否都值得长期保留；AGPL 引擎对未来发布方案是否可接受。

M0 上述审查问题仍可在后续审查中使用。本轮仅交付 L01 灰盒与技术证据，提交和推送后停止等待用户试玩；不得把这份清单或测试通过当作继续实施的许可。
