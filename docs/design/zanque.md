# 栈雀：随行维护终端

M1-R1 的角色与临时实体设计。新增内容只服务 C01-L01；未来角色弧是设计预留，不授权制作 S01 或其他单元。本设定补充[原有世界与人物](game-architecture.md)，保留林岑、衡务、许澈的身份和主线因果。

## 来源与真实用途

「栈雀」是澄湾空间调蓄站的小型折叠式维修辅助终端的工作称呼。它原本随检修员记录局部设备读数、辨认检修标记、照看工单里的回路交接。双片工具翼折起后便于停放在工作服的肩侧支架；它不是站级调度设备，也不是便携接驳器。

它的真实用途是让一线维护工作留下可核对的现场记录：哪扇检修门实际打开、哪里能落脚、原路是否还通。它没有隐秘的全站控制权、人的意识备份或知道结局的数据库。这个功能与原主线的「登记、设施实际状态和人的可达性不总一致」相呼应。

未来 S01 可让林岑从复压区的维护停放架取回栈雀，恢复当班工单的配对。它随后留在林岑肩侧，因为这本来就是检修员与辅助终端的工作方式；它需要在场的人判断陌生设备和确认安全。本轮不制作这段首次获得过程，L01 测试入口直接携带已经配对的终端。

## 它能知道什么

| 能力 | 边界与对白约束 |
| --- | --- |
| 观察近处灯色、机械动作和可见标记 | 不能透过墙观察，也不能凭一次看到出口就知道路线；具体对白由真实事件触发 |
| 比较自己刚见过的两个空间 | 可对穿折口后看见原出发地表示惊讶；不能在首次穿越前替玩家宣布落点和解法 |
| 读取部分标准维护接口 | 只识别本型号支持的设备；不能无线打开任意门、越过联锁或控制全站 |
| 保留简短工单观察 | 记录不等于理解，标签过期或线路改接时会误判；更正应来自玩家亲历的机械后果 |
| 与林岑及衡务短句沟通 | 没有全站人的实时名单，不知道许澈是否在封闭区，更不能提前解释灾后真相 |

栈雀好奇，习惯把新现象与做过的小修理相比较。偶尔猜错的是不影响解题的解释，不是故意提供假操作指令。它会承认「刚才没看清」；避免把每件事都变成笑话、持续插话或用亲昵称呼强求亲密。

## 与既有角色的关系

**林岑**仍是观察、尝试和决定路径的人。栈雀跟随其视线形成自己的局部观察，不替玩家瞄准、移动或操作。玩家可以关掉配音和字幕，所有必要操作仍能从设施反馈中理解。

**衡务**提供按规程汇总的设备状态，栈雀接触近处的实物。二者的信息来源不同，不设「绝对正确的伙伴对抗邪恶广播」结构。早期栈雀默认登记可信，碰到现场差异时先怀疑自己的识别；之后才学会把观察和登记并列提出。衡务保持克制工作语气，栈雀更口语、会迟疑和自我修正。两者使用同一播放队列控制注意力，不能各说各话。

**许澈**保留维护线值守者与现场参与者的作用。栈雀不能取代其敲击证据、手工旁路经验或后期共管责任，也不能越过被封闭区域替玩家远程探路。将来接触许澈后，它能学到「无法识别」不等于「不存在」。

## 长期成长预留

| 阶段 | 认识变化 | 必须由什么现场经历支撑 |
| --- | --- | --- |
| 前期 | 相信工单，乐于确认小设备恢复；开始留意绕行和返路 | 玩家实际走过折口、打开实体回路，后来看到恢复同时造成隔离 |
| 中期 | 从「我的识别可能错了」发展到同时报告读数与现场差异 | 标为无人处仍有活动、实际受电设备与标签不符、玩家进入维护线；不提前知道许澈 |
| 后期 | 理解「设备在线」不能替代「路对人可用」；表达有限的判断依据 | 玩家亲手验证独立旁路、落脚点和安全交接条件 |
| 最终选择 | 帮助回忆三种方案的已见事实，不给出唯一正确答案 | 原有三结局的实体交接仍由林岑操作、衡务说明系统代价、许澈承担现场职责 |

没有新增好感数值、隐藏日志解锁结局或伙伴自动解谜。未来对白和角色状态仍需逐章设计审查；本轮不实现这张表的剧情状态机。

## M1-R1 的临时三维表现

功能原型由 **12 个低面数 box mesh、5 个材质、288 个顶点、144 个三角形**组成。扁平叠层壳体约 18.9 × 11.5 × 11.5 cm，正面是两条矩形状态灯；两片侧向折叠工具翼、可见铰座、下侧工具夹和支架表达维修用途。它没有球形外壳、单圆眼或与既有作品相同的剪影。本轮几何不是正式模型和动画验收。首轮浏览器截图显示设备占据右下视野过多，因此整套部件、偏移和铰点统一缩至初版的 0.82 倍，挂载距离和门口收折参数保持不变。

使用玩家允许的**肩侧挂载**，不开发 NPC 寻路或悬浮机器人运动系统。挂载中心在当前第一人称相机局部 `(0.39, -0.28, 0.70)` m，位于画面右下。身体和工具翼保留中央瞄准区，普通场景目标的可见性仍需结合实际浏览器截图和真人体验检查。实体没有物理 body，不挡角色、机关或射线交互。

| 模式 | 临时反馈 |
| --- | --- |
| 待机 | 很小的局部上下活动，工具翼保持折起，双条状态灯稳定 |
| 说话 | 双灯亮度节奏、轻微机身颔动与工具翼活动；实际 `speaking` 由对白播放状态提供 |
| 观察 | 略偏转面板并舒展工具翼，表现正在辨认近处设施；不发出瞄准箭头或标出解法 |
| 暂停 | 停止活动和灯光节奏；恢复后继续，世界锚点仍取当前原生相机位姿 |
| 门口安全收折 | 接近有效折口时工具翼折起、主体快速退回肩侧视野外；走离落脚区后平滑展开，不影响移动和对话 |

挂载依据是**相机当前世界位姿**，包括 ArkGlide 原生折口对第一人称眼位的独立映射；没有追赶玩家世界坐标的插值。因此折口把相机映射到另一侧时，设备也立即落在映射后眼位的肩侧，不会从庭院低处穿墙飞向上层。`snap()` 只重锚设备，不更改玩家、相机、速度或传送门。

原型 visual 不是原生物理 traveler，不能让前伸的壳体比玩家先穿入锚面。关卡因此在接近已启用的 A1/B1 孔径附近、身体中心距门面约 1.3 m 时设置 `retracted`：挂载快速收回到局部 `(0.40, -0.34, -0.12)` m，位于相机后侧，工具翼同时收拢。穿越回调的 `snap()` 保留收折状态并立即锚定到新眼位；离开门口后才平滑展开。这是随身设备的可见动作，不处理或绕过玩家传送、碰撞和相机映射。近门及跨门画面仍由整关浏览器截图核查。

这是肩侧随身显示的功能原型。贴墙时的局部遮挡、不同宽高比下占屏比例、长时间观看是否分心，仍需真实试玩；不能把原型挂载当成已完成的全身角色表现。

## 实现契约与生命周期

源码为 [game/companion.js](../../game/companion.js)，仅调用固定版 ArkGlide 的 `visuals.createMaterial`、`visuals.createMesh`、材质 `update`、mesh `setPose` 和 `destroy`。几何、法线及四元数为游戏层数据；不读取 Babylon 私有实例，不引入模型依赖。

```js
const companion = createCompanion(ctx, { getPose: () => rig.camera.getPose() });
// 在原生相机本帧更新后执行：
companion.update(time.deltaTime, { speaking, observing, paused, retracted });
// 原生穿越、检查点恢复后：
companion.snap();
// 所属关卡销毁：
companion.dispose();
```

`update` 只平滑工具翼、局部挂载收折和几毫米范围的待机动作，不平滑跨空间的世界位置；`snap` 不重建 mesh 或材质。只读 `snapshot()` 给出模式、收折输入与进度、挂载距离、各部件世界位置、活动资源数和零碰撞体声明，供浏览器操作记录核查。重试复用同一套实体；完整停止时 `dispose()` 幂等释放，原生 owner cleanup 再作兜底。

本模块的原生 NullEngine 检查已执行：创建后 12 mesh + 5 material；120 次说话更新不增加资源；输入相机发生 21 m 位移与 90°旋转后，挂载距离保持一致、所有部件留在相机 1.15 m 内；观察/暂停模式、显式释放、原生 owner abort 后资源归零，物理 body 始终为零。这是坐标与生命周期技术检查，**不是浏览器画面检查、真实传送门体验或人工验收**；整关运行结果以 M1-R1 交付记录为准。


### 贴近实体结构时的避让

整关截图发现肩侧模型可能与上层栏杆相交后，L01增加原生 `physics.raycast` 挂载空间检查：对预期展开位置采样，忽略玩家与栈雀自身实体，遇到真实栏杆/墙体时请求相同的局部收折。检查始终针对展开位置，避免收起后检测空闲而来回抖动；不向玩家施力、不移动相机、不改变通关条件。门口收折仍先于原生穿越，离开结构后再平滑展开。最终浏览器已实际验证近门收折与贴栏避让：上层回望时命中真实 `GalleryGuard`，收折进度大于0.95，更新后的截图未见此前的栏杆穿插。其他贴墙角度、快速转向与不同设备上的舒适度仍需人工检查。
